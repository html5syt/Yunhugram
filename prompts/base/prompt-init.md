# 项目整体目标
使用Flutter UI + Rust 核心库（Dart FFI）基于 DrKLO/Telegram Android客户端改造、复刻，做一个接入“云湖” HTTP REST + WebSocket API 的即时聊天系统客户端。采用 Telegram 风格界面。需同时覆盖移动端与桌面端。

# 提示词架构说明
由于该项目涉及到多个技术栈、平台和模块，提示词将分为几个部分：
1. 所有的子功能描述和开发要求都放在 prompts/base 下。
2. 所有大型的修改和重构的提示词都放在 prompts/refactor 下。
3. 本init prompt 主要用于：
   1. 项目整体目标
   2. 提示词架构说明
   3. 整个项目的参考链接、参考代码库等各类参考信息
   4. 项目的整体开发要求，包括UI、代码风格、git使用等方面。
   各子功能描述和各自的开发要求将会在 prompts/base 下的各个文件中详细说明。
你需要严格遵守这些提示词的要求，确保开发出的代码符合项目整体目标和开发要求。
项目开发为分段进行，如果开发范围（子模块开发要求叙述）内包含了暂时未要求开发的部分，你需要先创建占位（比如主页下方tab栏的“社区”入口），后续要求到该部分时在进行填充/替换。

# 开发要求
## 1. 代码要求
1. 代码风格：遵循 Dart 和 Rust 官方的代码风格指南，保持代码整洁、可读性高。
2. 代码及代码文件组织结构：
   1. 模块化设计，使用函数等手段组织代码，确保代码易于维护和扩展。**严禁单文件长代码的情况！**
   2. 每个模块应有明确的职责，避免过度耦合。不能出现一个模块承担过多功能的情况。模块之间的依赖关系应清晰，避免循环依赖。
   3. 多个模块在代码文件中的排序遵循实际业务逻辑顺序，便于**人类**而不是agent理解和维护。
   4. 文件命名应清晰、具有描述性，遵循驼峰命名法或下划线命名法。代码文件应该使用文件夹进行组织，避免所有代码文件都放在同一目录下。
   5. 每个模块、函数等应包含必要的文档注释，说明其功能和使用方法。重点代码也需要注释，以便其他开发者理解代码逻辑。所有注释采用中文编写，简洁明了，**严禁在注释中出现记录“反复思考”等使注释冗长的行为，开发者看到的应该是清晰、准确的信息。**
   6. 代码中应避免硬编码，尽量使用配置文件或常量定义。
   7. 在被要求复刻某已有功能时，代码应尽量保持与原功能一致的逻辑和行为，除非有明确的优化或改进需求。
   8. 如果有功能/部分内容无法被实现，请按照以下2种情况处理：
      1. 其在后续开发中补上的代价较小，则可以暂时空缺继续开发其他内容，而无需停下来由我决策。该部分空缺的内容**必须在代码中明确标注，并在文档中说明原因和可能的解决方案。**
      2. 其在后续开发中补上的代价较大（如某些底层共享模块、架构等，改动后可能大量影响其他功能的），则需要**立即暂停开发**，并向我报告该问题，等待我的决策或是解决方案。
   9. 不要使用过多防御性编程，除非有明确的理由。过多的防御性编程会导致代码臃肿、难以维护和理解。
3. 测试编写与使用：
   1. 测试的编写应遵循测试驱动开发（TDD）原则，确保代码的正确性和稳定性。
   2. 开发为主，测试为辅。你应该把精力放在开发而不是编写测试代码上，测试是提供给你自动而不是由我人工验证自己写的代码是否正确的一个手段。测试不一定要覆盖所有代码，但必须覆盖你认为自己很容易出现错误的（比如复杂的交叉引用、长模块代码等）关键功能和核心模块。
   3. 仅运行必要的测试，避免不必要的测试运行，节省时间和资源。你应该在开发过程中根据需要选择性地运行测试，而不是每次都运行所有测试。
   4. 对于部分资源需求大的测试，注意本机资源消耗。

## 2. UI 要求
本项目的 UI 设计**应严格遵循 Telegram 的设计**，保持界面的一致性和用户体验的流畅性。
具体要求：
1. 严格遵循 Telegram 的设计规范，包括各类控件尺寸、颜色、字体、动画、贴图、交互及操作逻辑等。尽量直接使用telegram中原有的动画素材等。不得擅作主张。
2. UI要求跨平台、响应式布局，确保在不同设备和屏幕尺寸下都能保持良好的用户体验。你可以同时参考telegram的移动端和桌面端UI设计，确保在不同平台上保持一致的风格和操作逻辑。
3. 即使各子模块开发说明中包含一些新的UI设计或功能，也必须确保这些新设计与 Telegram 的整体风格保持一致，避免出现风格不统一的情况。
4. 关于UI一致性，尽量通过查阅 Telegram 开源代码库（参考信息中有）获取精确的设计信息。
5. 严格遵循并复刻telegram的UI系统，而不是自己设计一个新的UI系统。
6. 为了配合下面的性能和架构要求，UI开发不使用Material Design或Cupertino Design等Flutter自带的UI组件库，而是使用自定义的UI组件库，并参照telegram的源代码，对部分控件采用自绘而不是widget组装的形式，确保UI的一致性、高性能和可控性。

## 3. 性能要求与性能架构
本项目采取类似telegram + tdlib的架构，UI层与核心逻辑层分离，2个层之间的交互方法参考tdlib的做法。
逻辑层使用Rust编写，称为yhlib（全称YunhuLib），架构参考tdlib。
所有性能优化方法（包括但不限于自绘组件而不是使用widget拼凑、增量刷新、缓存组件大小等）均参考telegram的做法，**确保极致的UI性能和流畅度**。

## 4. Git、Github、Github Actions使用要求
1. Git的comment信息应清晰、简洁、准确地描述本次提交的内容和目的，遵循约定式提交规范（Conventional Commits），使用中文。
2. 每个agent对话轮次中，当每个功能模块制作/修改完成后都应该提交一次，当对话完成/需要测试ci时，才上传到云端。每次提交都应包含本次修改的功能模块的所有相关代码文件，确保提交的完整性和可追溯性。
3. 发布到GitHub公开仓库，应遵循开源协议，使用与telegram相同的开源协议。
4. Github Actions的使用：
   1. 每次提交并上传后，触发debug编译。
   2. 参考参考信息中给出的仓库ci实现，在tag或特定commit元数据下，使用自定义jks签名构建release版本，并上传到github release。
5. readme编写：同样参考第四点中指出的参考仓库，要求readme语言简洁，通俗易懂，同样遵循UI语言要求，**并且reamde不应该成为文档。**文档单独编写，语言要求同样遵循UI语言要求。
